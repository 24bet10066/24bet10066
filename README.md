## A little about how I think

I'm an engineering student at Chandigarh University focused on **Java, Spring Boot, backend development, and system design**. I'm interested in more than making an endpoint return `200 OK`: I want to understand the business rule behind it, the data it changes, and how the system behaves when the happy path ends.

- 🧩 **Start with the real problem.** Understand the people, process, and constraints before choosing a solution.
- 🛠️ **Prefer dependable over flashy.** Clear business rules, consistent data, useful tests, and visible failures matter.
- ⚙️ **Automate with a reason.** Use algorithms or AI when they improve a real outcome, not just to add another technology to the stack.
- 📈 **Keep learning by building.** Work on real workflows, test assumptions, and improve what the evidence says needs improving.

## 🤖 ML & MLOps: learning beyond the model

I'm building foundations in the machine-learning lifecycle: preparing data, evaluating models, comparing metrics, and understanding reproducibility, deployment, and monitoring.

One area I'm exploring is parts-demand forecasting for Wrenchy. The rule I want to follow is simple: **a model has to earn its place**. It should be evaluated on genuine historical data against a sensible baseline before anyone trusts its predictions. Until that evidence exists, it's learning work, not a proven business result.

## My usual approach

`Understand the workflow → define the rules and data → build the API → test failure cases → deploy → measure and improve`

The bugs that interest me most are often the unglamorous ones: duplicate actions, inconsistent stock, unclear ownership, missing history, and failures nobody notices until the business pays for them.
